# コーディング規約

Python の標準的な慣習（PEP 8）に従う。photo-frame から移植するコードの書きぶりとも整合させる。

## 命名規則

- 変数・関数・メソッド: `snake_case`
- クラス: `PascalCase`（例: `ImmichAPI`, `ConfigManager`, `PhotoCache`）
- 定数: `UPPER_SNAKE_CASE`
- 非公開メンバ: 先頭に `_`（例: `_load()`）
- ファイル・モジュール: `snake_case.py`

## フォーマット

- インデントは半角スペース4つ
- 行長は 100 文字を目安とする（PEP 8 の 79 は厳格すぎるため緩和）
- 文字列は基本的にシングルクォート、埋め込みには f-string を使う

## 型ヒント

- **新規に書くコードには型ヒントを付ける。** 特に `photo_cache.py` や `gui/` 配下の
  新規モジュールでは、公開関数・メソッドのシグネチャに付与する。
- photo-frame から移植するコードは型ヒントが無い。移植時に付与するのが望ましいが、
  移植の正しさを優先し、付与のために構造を変えない。

## コメント・docstring

- コメント・docstring は**日本語**で書く（photo-frame の既存コードに合わせる）。
- クラスと公開メソッドには docstring を付ける。既存コードのスタイルは
  `""" 説明 """`（前後にスペース）。移植コードではこれを維持する。
- 「何をしているか」ではなく「なぜそうしているか」を書く。
  特に**メモリ制約のために採った実装**には理由を残す（後から素直な実装に戻されるのを防ぐため）。

## ログ

- `kivy.logger.Logger` は使えない。標準ライブラリの `logging` を使う。
  photo-frame からの移植時は必ず置き換えること。
- 実機ではコンソールログが唯一の調査手段になる。写真の取得・キャッシュヒット/ミス・
  センサー検知・画面電源の遷移は残す。ただし毎フレーム出力するログを入れない。

## その他のルール

- **設定値をハードコードしない。** `config_manager.py` 経由で読む。
  新しい設定キーを足すときは「対で更新が必要な箇所」（`.claude/architecture.md`）を確認する。
- 秘匿情報（Immich の URL / API キー）はリポジトリにコミットしない。
  `config.py` は `.gitignore` 対象とし、サンプルのみを追跡する。
- 例外を握りつぶさない。ネットワーク断はキャッシュへフォールバックする正常系として扱い、
  それ以外は握らずログに残す。
